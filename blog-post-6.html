Passkeys in Entra ID
Phishing-Resistant MFA, End to End

Your homelab already has MFA, the kind a convincing fake sign-in page can still relay. Replace it with device-bound passkeys in Microsoft Authenticator (or a FIDO2 security key, if you have one), enforced by a Conditional Access authentication strength. Admins first, break-glass excluded, report-only before On.

By Masood RazaIAM Architect · 24+ years · Identity security

Post 2 gave the homelab Conditional Access and MFA. That's the right first step, but it isn't the last one. A push approval or a one-time code proves that someone has the phone. It doesn't prove that the person is signing in to the real Microsoft sign-in page. Adversary-in-the-middle phishing kits rely on exactly that gap: the user types the code into a proxy, and the proxy passes it on.

Passkeys close that gap by design. Microsoft describes them as using "origin-bound public-key cryptography": the credential is tied to the site it was created for, and every sign-in needs the user to be present and unlock it on their own device. A fake domain can't ask for a passkey that was never registered to it.

This guide rolls passkeys out in the same tenant from Post 2 (iamlab.onmicrosoft.com). It follows the order you'd use in production: protect the way back in, enable the method, register the people who matter most, enforce it in report-only mode, and only then turn it on.

By the end of this guide, you will have:

  • The Passkey (FIDO2) method enabled with a passkey profile that allows only attested, device-bound passkeys
  • A passkey in Microsoft Authenticator, registered and checked with Microsoft Graph PowerShell (plus the security key route, if you have a key)
  • Temporary Access Pass (TAP) set up for bootstrap and recovery
  • A custom authentication strength that accepts only your approved authenticators, next to the built-in Phishing-resistant MFA strength
  • A Conditional Access policy that requires phishing-resistant MFA for admin roles, tested in report-only mode before it was switched on
  • Two break-glass accounts that are excluded from enforcement and can still sign in if everything else breaks
  • A pilot policy for regular users that avoids the best-known passkey registration trap
Prerequisites

The Post 2 homelab tenant, a Global Administrator account you use for the lab, and a phone on iOS 17+ or Android 14+ with Microsoft Authenticator installed. A FIDO2 security key is optional. Microsoft recommends one for break-glass accounts in production, but every hands-on step in this lab works with Microsoft Authenticator alone. The Conditional Access phases need Microsoft Entra ID P1 (a P2 trial also works). If the 30-day trial you started in Post 2 has expired, check Billing > Licenses before Phase 4.

What Needs a Licence

Free vs P1: What You Can Do Without Paying

The passkey method itself costs nothing. Microsoft's documentation says passkeys (FIDO2) "are available in all Microsoft Entra ID editions, including Microsoft Entra ID Free. No extra licenses are required." Enforcing passkeys for specific users and apps is a Conditional Access feature, and that needs P1.

CapabilityLicence
Passkey (FIDO2) method, passkey profiles, attestation, key restrictionsFree (no extra licence)
Users registering passkeys in Authenticator or on a security keyFree
Temporary Access PassEntra ID P1
Conditional Access, authentication strengths, report-only modeEntra ID P1
Authentication methods activity report and the userRegistrationDetails APIEntra ID P1 or P2

On a Free tenant you can still do Phases 1–3 and register everyone. Users then add a passkey by first completing their existing MFA, because Entra ID asks for MFA within the last five minutes before a passkey can be registered. TAP and enforcement wait until you have P1.

Phase 0

Protect the Way Back In First

Every phishing-resistant rollout that goes wrong goes wrong the same way: an admin enforces a policy they can't yet satisfy. So before you enable anything, make sure there's a way back in that this policy can't block.

Microsoft's emergency access guidance says to keep two or more cloud-only accounts that use the *.onmicrosoft.com domain and hold Global Administrator. It recommends passkeys (FIDO2) as their authentication method, using a method that is different from the one your normal admin accounts use. Post 2 told you to exclude "your break-glass admin". This is where you make that real.

StepAction
1Create bg-admin-01@iamlab.onmicrosoft.com and bg-admin-02@iamlab.onmicrosoft.com as cloud-only users with long, random passwords. Store the passwords offline.
2Assign both Global Administrator as a permanent active assignment, not an eligible one, if you use PIM.
3Create a cloud security group SG-EmergencyAccess and add both accounts. Every enforcing Conditional Access policy in this guide excludes this group.
4Create a second cloud security group SG-Passkey-Pilot. Add your lab admin account, Sarah Chen and Raj Patel.

The screenshots in this post come from my own lab run, with tenant names, IDs and accounts masked. A few lab names differ from the ones in the steps: my pilot group is IFL-Passkey-Pilot and my custom strength is Passkeys only.

Different method on purpose

Your daily admin account gets a passkey in Microsoft Authenticator. The break-glass accounts need a phishing-resistant method that is different from that one, so that a lost phone or an Authenticator problem can't take out both paths. That separation is the point of Microsoft's "different from your normal admin method" advice, and Microsoft's own example is a FIDO2 security key for the emergency accounts. In production, buy keys from a vendor on Microsoft's list of attestation-capable FIDO2 providers. No key in your homelab? Register the break-glass passkeys in Authenticator on a separate device that isn't your daily phone. That's a lab compromise, not a production design, so write it down as a gap.

Microsoft also recommends alerting on every use of an emergency access account (Azure Monitor or Microsoft Sentinel both work) and validating the accounts at least every 90 days. In a homelab, put a calendar reminder in for the 90-day test, as a minimum.

Phase 1

Enable Passkeys with a Passkey Profile

Passkey profiles are now generally available. A profile is a named set of rules: which passkey types are allowed (device-bound, synced or both), whether attestation is enforced, and which authenticator models (AAGUIDs) are allowed or blocked. You assign profiles to groups.

Opt in to passkey profiles

StepAction
1Sign in to the Microsoft Entra admin center as at least an Authentication Policy Administrator
2Browse to Entra ID > Authentication methods > Policies > Passkey (FIDO2)
3If you see the banner offering passkey profiles, select it and opt in. Your existing global settings move into a Default passkey profile.
4Make sure Allow self-service set up is Yes. This is a global setting, and users can't register passkeys without it.
One-way door

Opting in to passkey profiles can't be undone. In a lab that's fine. In production, read the current settings first (the Graph snippet below does that) so you know what goes into the Default profile. Microsoft has also been moving existing passkey-enabled tenants to profiles automatically, so the banner may already be gone. If it is, you're already on profiles.

You may also see a Passkey auto-enablement banner on the Passkey (FIDO2) page. It says users who are enabled for SMS or voice authentication will be put in scope for passkeys under a system-managed profile that allows all passkey types. Read it before you assume only your target groups can register a passkey.

Create the profile

Microsoft Learn documents up to three profiles, including the Default. The admin center in my tenant already says up to 10 are supported, so the limit is moving; plan around three until the documentation catches up. This lab uses one custom profile for everyone in scope:

StepAction
1Under Passkey (FIDO2), select Configure > + Add passkey profile and name it PK-Attested-DeviceBound
2Enforce attestation: Yes
3Passkey types: Device-bound only
4Target specific authenticators: leave this off for now. You'll turn it on in Phase 2, once your first passkeys are registered and you can read their AAGUIDs.
5On Enable and Target, enable the method and add SG-Passkey-Pilot and SG-EmergencyAccess, both assigned PK-Attested-DeviceBound
6Save

Why these choices:

  • Attestation checks during registration that the authenticator really is the make and model it claims to be. It's checked only at registration. If you turn it on later, passkeys registered earlier aren't blocked. That's why it's on from day one here.
  • Device-bound only keeps the private key on one phone or one key. Synced passkeys (iCloud Keychain, Google Password Manager) are a perfectly good choice for the wider workforce. Microsoft's guidance is to treat them as phishing-resistant but unattested, and attestation can't be enforced for them. For admins, device-bound and attested is the stronger stance.
  • If a user is in more than one profile, a passkey that satisfies any of them is accepted. If a user is in an excluded group, they can't use passkeys at all. Keep exclusions on this method empty unless you mean it.

Check the result from PowerShell. This only reads the policy:

Read the Passkey (FIDO2) policy
Connect-MgGraph -Scopes "Policy.Read.AuthenticationMethod" $fido2 = Get-MgPolicyAuthenticationMethodPolicyAuthenticationMethodConfiguration ` -AuthenticationMethodConfigurationId "Fido2" $fido2.State $fido2.AdditionalProperties.isSelfServiceRegistrationAllowed $fido2.AdditionalProperties.passkeyProfiles | ConvertTo-Json -Depth 5

In the v1.0 response, each profile shows its passkeyTypes, attestationEnforcement and keyRestrictions, and each include target lists its allowedPasskeyProfiles.

Turn on Temporary Access Pass (P1)

TAP is a time-limited passcode that an admin issues so that a user can sign in and register a passkey without any other method, for example on day one or after losing a phone.

StepAction
1Entra ID > Authentication methods > Policies > Temporary Access Pass
2Enable it and target SG-Passkey-Pilot
3Select Configure. The defaults are a 1-hour minimum and default lifetime, an 8-hour maximum, one-time use off and a length of 8. Set One-time use to Yes for this lab.
4Save
Phase 2

Register the Passkeys

Passkey in Microsoft Authenticator (your admin account)

This is the main hands-on route in this lab, and the only one you need if you don't own a security key. Authenticator passkeys need iOS 17+ or Android 14+. The registration flow Microsoft recommends starts in the app itself:

StepAction
1In Authenticator, add your work or school account (or tap the existing account) and choose Create a passkey
2Complete MFA, and set a device screen lock if prompted
3When asked, enable Authenticator as a passkey provider. On iOS 18 that's Settings > General > AutoFill & Passwords (iOS 17: Settings > Passwords > Password Options): turn on AutoFill Passwords and Passkeys and select Authenticator under Autofill From. On Android, open Passwords & accounts and select Authenticator under Additional providers.
4Finish. The account in Authenticator now shows a passkey.

You can also start from Security info in a browser (+ Add sign-in method > Passkey in Microsoft Authenticator). That route uses a QR code and Bluetooth between the computer and the phone, so it needs Bluetooth and internet access on both. It also needs the cross-device endpoints Microsoft lists to be reachable: cable.ua5v.com, cable.auth.com, app-site-association.cdn-apple.com and app-site-association.networking.apple. On iOS, attested passkeys can only be registered directly in the Authenticator app, which is another reason to start there.

Passkey on a FIDO2 security key (optional, for break-glass accounts)

If you have a FIDO2 security key, this is how the break-glass accounts get theirs. Any FIDO2 key that supports attestation works; this guide doesn't depend on a particular model. If you don't have one, register the break-glass passkeys in Authenticator on a separate device (see Phase 0) and use the same TAP bootstrap below. Sign in to Security info (https://aka.ms/mysecurityinfo) as bg-admin-01. Then:

StepAction
1Sign in with MFA
2Add sign-in method > Passkey > Next
3When the browser asks where to save the passkey, choose Use another device or More options, then Security key
4Insert or tap the key, set or enter its PIN, and touch it when prompted
5Give the method a recognisable name (for example BG key 1) and select Done

Repeat for bg-admin-02. The break-glass accounts are new and have no MFA method yet. This is exactly the bootstrap problem TAP solves. Issue each one a one-time TAP first:

Issue a one-time TAP for bootstrap
Connect-MgGraph -Scopes "UserAuthMethod-TAP.ReadWrite.All" $tap = New-MgUserAuthenticationTemporaryAccessPassMethod ` -UserId "bg-admin-01@iamlab.onmicrosoft.com" ` -BodyParameter @{ isUsableOnce = $true; lifetimeInMinutes = 60 } $tap.TemporaryAccessPass # shown once - hand it over out of band

Creating a TAP for another user needs Authentication Administrator. For admin accounts such as these Global Admins, it needs Privileged Authentication Administrator. A user has only one usable TAP at a time, so creating a new one replaces the old one. After someone signs in with a one-time TAP, they have 10 minutes to finish registering, so have the key (or the second device) ready before you sign in.

The same thing in the admin center: open the user, then Authentication methods > + Add authentication method > Temporary Access Pass.

TAP + interrupt mode

If a user is in scope of the SSPR registration policy or the Identity Protection MFA registration policy, signing in with a TAP can put them into "interrupt mode" registration, and that mode doesn't support passkey (FIDO2) registration. If the passkey option doesn't appear, go straight to https://aka.ms/mysecurityinfo after the TAP sign-in.

Verify what was registered

Inspect a user's passkeys
Connect-MgGraph -Scopes "UserAuthMethod-Passkey.Read.All" Get-MgUserAuthenticationFido2Method -UserId "bg-admin-01@iamlab.onmicrosoft.com" | Select-Object DisplayName, Model, AaGuid, AttestationLevel, PasskeyType, CreatedDateTime

You want AttestationLevel to be attested and PasskeyType to be deviceBound. Write down the AaGuid: it identifies the make and model of the authenticator (Authenticator on iOS and Android each report their own, and a security key reports its model's). (If PasskeyType comes back empty in your module version, check AdditionalProperties.) To read other users' passkeys, the signed-in account needs at least Global Reader or Authentication Administrator.

Lock the profile to approved authenticators

Now that you know the AAGUIDs, go back to Passkey (FIDO2) > Configure > PK-Attested-DeviceBound:

StepAction
1Target specific authenticators: On, behaviour Allow
2+ Add AAGUID > Microsoft Authenticator. This adds the Authenticator AAGUIDs: 90a3ccdf-635c-4729-a248-9b709135078f (iOS) and de1e552d-db1d-4423-a619-566b625cdc84 (Android).
3If you registered a security key, add its AAGUID from the PowerShell output. Skip this step if you only use Authenticator.
4Save
Key restrictions bite both ways

Unlike attestation, key restrictions apply at registration and at sign-in. If you later remove an AAGUID from the allow list, every passkey with that AAGUID stops working for sign-in straight away, including the break-glass passkeys. Change this list carefully.

Phase 3

Pick the Authentication Strength

Conditional Access doesn't say "require passkeys" directly. It says "require an authentication strength", which is a named list of acceptable method combinations. There are three built-in strengths, and you can't change them:

Built-in strengthAccepts, for exampleNotes
Multifactor authenticationPassword + push/OTP/SMS/voice, passkeys, WHfB, TAPTAP satisfies this strength only
Passwordless MFAPasskeys, WHfB, multifactor CBA, Authenticator phone sign-in
Phishing-resistant MFAPasskeys (FIDO2), Windows Hello for Business / platform credential, multifactor certificate-based authenticationAuthenticator phone sign-in and TAP don't satisfy it

You can list them yourself:

List authentication strengths
Connect-MgGraph -Scopes "Policy.Read.AuthenticationMethod" Get-MgPolicyAuthenticationStrengthPolicy | Select-Object DisplayName, PolicyType, @{n='Allowed';e={$_.AllowedCombinations -join ', '}}

The built-in Phishing-resistant MFA strength accepts any passkey the method policy allows. That's the right choice for the admin policy, because it also covers Windows Hello for Business if you add it later. For tighter control, create a custom strength that accepts only your approved models:

StepAction
1Sign in to the Microsoft Entra admin center as at least a Security Administrator
2Entra ID > Authentication methods > Authentication strengths > New authentication strength
3Name: Passkey - Approved authenticators
4Select Passkeys (FIDO2), then Advanced options > + Add AAGUID. Add the two Authenticator AAGUIDs, plus your security key's AAGUID if you use one.
5Save

You can create up to 15 custom strengths. A user who signs in with a passkey that isn't on the list is stopped with "You can't get there from here." You also can't delete a strength while a Conditional Access policy still references it.

Phase 4

Enforce for Admins: Report-Only, Then On

Microsoft ships a Conditional Access template for exactly this policy (Require phishing-resistant multifactor authentication for administrators). You can create it from the template or build it by hand:

StepAction
1Sign in as at least Conditional Access Administrator. Go to Entra ID > Conditional Access > Policies > New policy. (The menus have moved since Post 2. "Protection" is no longer in the path.)
2Name: CA-Admins-PhishingResistant
3Users > Include > Select users and groups > Directory roles: the 14 roles Microsoft recommends at minimum: Global, Application, Authentication, Billing, Cloud Application, Conditional Access, Exchange, Helpdesk, Password, Privileged Authentication, Privileged Role, Security, SharePoint and User Administrator
4Users > Exclude > Users and groups: SG-EmergencyAccess
5Target resources: All resources
6Grant > Grant access > Require authentication strength > Phishing-resistant MFA
7Enable policy: Report-only, then Create
Two limits worth knowing

Directory-role targeting covers built-in roles only. Custom roles and roles scoped to an administrative unit aren't enforced this way. Also, one policy can't use both Require multifactor authentication and Require authentication strength. If an older Post 2 policy requires MFA, leave it alone. Conditional Access combines policies, so the admins have to satisfy both.

Leave it in report-only mode for a few days while you sign in normally as your admin: sometimes with the passkey, sometimes deliberately with password and push.

My lab policy is a cut-down version of this one. To keep the test small, it targets the pilot group instead of directory roles and uses the custom Passkeys only strength, and it stays in Report-only. The screens are the same ones you'll use for CA-Admins-PhishingResistant.

Security defaults come first

If your lab tenant still has security defaults enabled, the admin center lets you save Conditional Access policies in Report-only, but you have to disable security defaults before any policy can be On. Have your replacement baseline policies ready (Post 2) before you flip that switch, so the tenant is never left without MFA.

Phase 5

Test and Verify in the Sign-In Logs

Go to Entra ID > Monitoring & health > Sign-in logs, open one of your admin sign-ins, and check three tabs:

  • Authentication Details shows the sequence of methods used. A passkey sign-in should show the passkey as the method.
  • Conditional Access shows enforced policies and their result (Success, Failure, Not applied).
  • Report-only shows what CA-Admins-PhishingResistant would have done.
Report-only resultWhat it means here
Report-only: SuccessThe sign-in already met the policy, for example you used the passkey
Report-only: User action requiredThe policy applied, and you'd have been prompted for a phishing-resistant method (for example, you used password + push)
Report-only: FailureThe policy applied, but a non-interactive control wasn't satisfied (for example a block, or a failed device-compliance check). You shouldn't see this for this policy.
Report-only: Not appliedThe policy didn't match, for example a break-glass sign-in, which is excluded

Before you switch to On, you need three things:

  1. Every admin account in scope shows a passkey (Get-MgUserAuthenticationFido2Method returns at least one attested, device-bound passkey)
  2. Sign in as each break-glass account and confirm Report-only: Not applied. Then sign out.
  3. No admin sign-in you rely on (portal, PowerShell, Graph Explorer) shows User action required that you can't satisfy with a passkey

For a tenant-wide view, the registration report shows who is ready. It needs P1 or P2, needs AuditLog.Read.All, and can lag by up to 36 hours:

Who is passwordless-capable?
Connect-MgGraph -Scopes "AuditLog.Read.All" Get-MgReportAuthenticationMethodUserRegistrationDetail -All | Where-Object { $_.IsAdmin } | Select-Object UserPrincipalName, IsPasswordlessCapable, @{n='Methods';e={$_.MethodsRegistered -join ', '}}

When all three checks pass, open the policy, set Enable policy to On, and save. Then sign in as your admin in a private browser window. If you start with a password, that's expected to work for the first step. Conditional Access is evaluated after the initial authentication, so you can still enter a password, but you must then use a phishing-resistant method before you can continue. Choose Sign-in options on the sign-in page to go passwordless from the start.

Phase 6

Pilot for Regular Users, Without the Registration Trap

Now extend enforcement to SG-Passkey-Pilot. There's one trap that Microsoft documents and that catches a lot of rollouts:

The All-resources loop

If a Conditional Access policy requires a passkey for All resources and a user doesn't have one yet, they get stuck in a loop when they try to add one in Authenticator: signing in to Authenticator is itself blocked by the policy that needs the passkey. Signing in to Authenticator with a TAP avoids the loop. All-resources policies with Require approved client app or Require app protection policy block Authenticator passkey registration too, because Authenticator doesn't support those controls.

The fix for a pilot is to target the apps people actually use, rather than All resources:

StepAction
1New policy CA-Pilot-Passkey-Apps
2Users > Include: SG-Passkey-Pilot. Exclude: SG-EmergencyAccess
3Target resources > Select resources: the AWS IAM Identity Center enterprise app from Post 3, plus Office 365
4Grant > Require authentication strength > Passkey - Approved authenticators (your custom strength)
5Report-only first. Switch to On once the pilot users show Report-only: Success.

Sarah or Raj can now test the pilot: sign in to the AWS access portal from Post 3, choose the passkey, approve on the phone, and land in AWS with no password and no push. The custom strength and the profile's allow list back each other up. If you later loosen the profile (for example, a second profile that allows synced passkeys), anyone who signs in to these apps with a passkey that isn't on the strength's list is stopped at "You can't get there from here".

Rollout

Rollout Tips That Carry Over to Production

  • Plan for passkeys as a first MFA method. Microsoft 365 message center post MC1450133 (updated 26 Oct 2026) says password-only users will be able to register a passkey as their first MFA method, without adding SMS or voice first. Phase 1 (synced passkeys, Entra passkeys on Windows and FIDO2 security keys) starts rolling out in early November 2026. Phase 2, which adds the Authenticator passkey used in this lab, starts in early January 2027. Users who are enabled for passkeys will then be prompted to register one by default, including when registration is triggered by a Conditional Access authentication strength, so check which groups your passkey profiles target before it reaches your tenant.
  • Use a registration campaign to nudge users. Entra ID > Authentication methods > Registration campaign can now target Passkey (FIDO2). Users are prompted after they complete MFA. In the Enabled state you choose the snooze length (0–14 days) and whether snoozing is limited. In Microsoft managed state, Microsoft sets those values. The campaign doesn't prompt guests for passkeys, and it doesn't prompt Linux users.
  • Make TAP your recovery process, not a back door. Keep it one-time, issue it only after the helpdesk has verified who is calling, and remember that only users in the TAP policy's scope can use one.
  • Admins first, then a pilot, then the wider workforce. Each stage gets its own report-only period. Move groups into scope; don't widen the conditions of a policy that's already On.
  • Decide synced vs device-bound by population. Microsoft recommends security keys (or Authenticator passkeys) for privileged and highly regulated users, and positions synced passkeys as the low-cost option for most other users. A second passkey profile (you're allowed three) is how you give each group its own rules.
  • Watch for "Register security info" policies. Users still have to satisfy any Conditional Access policy that targets the Register security information user action. If that policy itself requires a passkey, new users can't get started without a TAP.
Pitfalls

Pitfalls I'd Check First When It Breaks

SymptomLikely cause
"Passkey" missing from Add sign-in methodUser not in the Passkey (FIDO2) targets, in an excluded group, or Allow self-service set up is No
Registration fails with attestation onOn iOS, attested passkeys can only be registered directly in the Authenticator app, not via the browser QR flow. Attestation also relies on Apple and Google services: heavy load can make registration fail (try again), and an outage blocks it until the service is back.
"A passkey already exists" in AuthenticatorThe passkey was saved locally but never registered with Entra ID. Delete it in Authenticator and register again.
Authenticator passkey can't be registered at allAn All-resources passkey policy (the loop above), or an approved-client-app / app-protection CA policy
Passkey problems after a UPN changePasskeys can't be updated for a new UPN. Delete the old passkey in Security info and add a new one.
Guest users can't registerGuests aren't supported for passkey registration
Works in the personal Android profile, not the work profileAndroid passkeys are used only from the profile they're stored in
Hybrid-joined Windows can't use the security keyHybrid-joined devices must run Windows 10 version 2004 or later (Microsoft Entra joined devices work best on 1903 or later)
A passkey that used to work is rejected at sign-in after a policy editIts AAGUID was removed from the profile's allow list or from the custom strength
Can't save another passkey profileThe Passkey (FIDO2) policy has a 20 KB size limit. Consolidate the targeted groups.

What to Build Next

  • Conditional Access baseline: put this admin policy alongside block legacy authentication, require MFA for all users, and risk-based policies as one documented baseline
  • Windows Hello for Business or platform credentials: the other phishing-resistant methods the built-in strength already accepts
  • Synced passkeys for the wider workforce: a second passkey profile with different rules for non-admin users
  • Automated readiness reporting: feed userRegistrationDetails into the n8n instance from Posts 4 and 5, and post a weekly "who still isn't passwordless-capable" summary

Six posts in, the homelab has gone from "has MFA" to "can't be phished into giving away an admin session". That's the change that matters most against the attacks hitting identity teams right now.
