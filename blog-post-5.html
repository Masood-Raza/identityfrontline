Automate the Leaver
Offboarding Without the Loose Ends

Disabling the account in Active Directory feels like offboarding. It is not. The SSO session can still be alive, the SCIM-synced AWS access can still be active, and the mailbox just goes silent. Build the n8n workflow that closes those gaps automatically, starting within a minute of the disable.

By Masood RazaIAM Architect · AI + Security Automation · Fortune 500 SME

Post 4 ended with a list of what to build next, and the first item on it was this: the Leaver workflow. Not because it is the hardest automation to build — it is actually simpler than onboarding — but because it is the one most environments get wrong, including plenty of real enterprises with full-time IAM teams.

Across the audits and reviews I have done, the single most common finding — at nearly every maturity level — is not a missing Conditional Access policy or a weak password rule. It is enabled accounts and live access that belong to people who no longer work there. That finding exists because "offboarding" usually means one action: disable the AD account. Everything downstream of that account — federated sessions, synced groups, mailbox access — is left to expire on its own schedule, which can be days, weeks, or never.

This guide builds the workflow that actually closes those gaps, using the exact same homelab and the exact same n8n instance from Post 4.

By the end of this guide, you will have:

  • A workflow that starts within about a minute of a user being disabled in Active Directory
  • Automatic revocation of every active Entra ID sign-in session — not just the account disable
  • Automatic group removal (in AD for synced groups, in Entra ID for cloud-only groups) that cascades through SCIM to pull the user's AWS IAM Identity Center access on the next provisioning cycle
  • A step to end the user's active AWS sessions, not just their future sign-ins
  • A mailbox that gets an auto-reply and, where your policy allows it, a forwarding rule instead of going silent
  • Manager notification and a compliance-ready audit log entry
  • The second half of a Joiner-Mover-Leaver portfolio story — most candidates only ever show the first half
Prerequisites

You need the n8n instance and the "IAM – New User Onboarding" workflow from Post 4, and the Entra ID ↔ AWS IAM Identity Center SSO from Post 3. This guide assumes both are running. The mailbox steps also need the test user to have a licensed Exchange Online mailbox.

Why This Matters

The Leaver Nobody Finishes

Joiner automation gets built first because it is urgent and visible — a new hire blocked on day one generates a ticket within the hour. Mover automation gets built second because it is annoying enough to justify the effort. Leaver automation gets built last, if at all, because a disabled account is quiet. Nobody files a ticket complaining that their offboarding was incomplete. The exposure just sits there until an audit, an access review, or an incident finds it.

Five steps. In a manual process, each one is a separate ticket, owned by a different team, with no guarantee any of them happen the same day — or at all. Automated, they happen in sequence, every time, starting within a minute of the disable.

The Gap

What "Disable the Account" Misses

This is the part that surprises people who are new to federated identity: disabling a user in Active Directory does not end their active sessions anywhere else.

  • Federated SSO sessions survive the disable. The SAML/SCIM setup from Post 3 means a user signs in to AWS IAM Identity Center through Entra ID. Entra ID only learns about the AD disable at the next Entra Connect sync (every 30 minutes by default), and even then it does not end sessions that already exist. AWS keeps its own session too. Existing sessions keep working until they expire.
  • Group membership is usually forgotten. The SCIM provisioning from Post 3 deprovisions AWS access when the user is removed from the synced group — but only if someone remembers to remove them. Disabling the account does not touch group membership at all.
  • The mailbox just stops. No auto-reply, no forwarding, nothing to tell senders the person is gone. Important email either bounces or disappears into a mailbox nobody is reading.
  • There is no consistent record. When an audit asks "prove this person's access was revoked within 24 hours of termination," a disabled AD account with no timestamped log of session revocation, group removal, and mailbox handling is not proof of anything.
The gap that matters most

Entra ID only learns about the AD disable at the next sync, and even then existing access tokens and app sessions are not ended. Sessions are ended explicitly, via the Microsoft Graph revokeSignInSessions endpoint, or implicitly, when tokens expire on their own schedule.

Revoking Entra sessions stops new sign-ins through Entra ID. It does not end sessions an app has already issued. AWS IAM Identity Center keeps its own session, and console or CLI role sessions run until the permission set's session duration expires (up to 12 hours). To cut AWS off fully, also end the user's active sessions in IAM Identity Center and keep permission-set session durations short.

Phase 1

Detect the Leaver Event

Same pattern as Post 4's onboarding trigger, mirrored for the opposite event. In production, HR marking someone as terminated fires this. In the homelab, a PowerShell script watches AD for accounts that just became disabled and sends their details to a new n8n webhook.

Create the Second Webhook in n8n

StepAction
1In n8n, click New Workflow
2Name it: IAM - Leaver Offboarding
3Add a Webhook node, HTTP Method POST
4Copy the Test URL for the PowerShell script below

Create the PowerShell Trigger Script

On DC01, create a script that polls for accounts disabled since the last check and posts them to the new webhook:

Monitor-DisabledUsers.ps1
# Monitor AD for newly-disabled users and trigger the Leaver workflow # Run on DC01 (which also runs Entra Connect in this lab), elevated. Import-Module ActiveDirectory Import-Module ADSync $webhookUrl = "YOUR_N8N_LEAVER_WEBHOOK_URL_HERE" $checkInterval = 60 # seconds $builtIns = @("krbtgt", "Guest", "DefaultAccount", "WDAGUtilityAccount") # Record every account that is ALREADY disabled at startup, # so only new disables fire the webhook $knownDisabled = @{} Get-ADUser -Filter { Enabled -eq $false } | ForEach-Object { $knownDisabled[$_.ObjectGUID.ToString()] = $true } Write-Host "Monitoring for newly-disabled AD users..." -ForegroundColor Cyan while ($true) { $disabledUsers = Get-ADUser -Filter { Enabled -eq $false } -Properties Title, Department, Manager foreach ($user in $disabledUsers) { $key = $user.ObjectGUID.ToString() if ($knownDisabled.ContainsKey($key)) { continue } $knownDisabled[$key] = $true if ($builtIns -contains $user.SamAccountName) { continue } # 1. Remove AD group memberships. AD is the source of # authority for synced groups such as SG-Cloud-Admins. # Domain Users is the primary group and stays. $groups = @(Get-ADPrincipalGroupMembership $user | Where-Object Name -ne "Domain Users") foreach ($g in $groups) { Remove-ADGroupMember -Identity $g -Members $user ` -Confirm:$false } # 2. Push the disable and the group changes to Entra ID # now, instead of waiting for the 30-minute schedule Start-ADSyncSyncCycle -PolicyType Delta | Out-Null $managerEmail = $null if ($user.Manager) { $managerEmail = (Get-ADUser $user.Manager ` -Properties EmailAddress).EmailAddress } $payload = @{ samAccountName = $user.SamAccountName displayName = $user.Name email = $user.UserPrincipalName title = $user.Title department = $user.Department managerEmail = $managerEmail adGroupsRemoved = @($groups | ForEach-Object Name) detectedAt = (Get-Date).ToString("o") } | ConvertTo-Json Invoke-RestMethod -Uri $webhookUrl ` -Method POST ` -Body $payload ` -ContentType "application/json" Write-Host "Triggered offboarding for: $($user.Name)" ` -ForegroundColor Yellow } Start-Sleep -Seconds $checkInterval }
What this script does

At startup it records every account that is already disabled, including built-ins such as krbtgt and Guest, so only new disables fire. Then, every 60 seconds, it checks for AD accounts with Enabled -eq $false and fires the webhook once per new disable while the script is running (an account disabled while the script is stopped is treated as already handled on the next start). For each leaver it removes the AD group memberships, because synced groups can only be changed in AD, and runs an Entra Connect delta sync (Start-ADSyncSyncCycle -PolicyType Delta) so the disable and the removals reach Entra ID in a minute or two rather than at the next scheduled sync. It also looks up the user's manager so the notification step later has someone to notify. The payload's detectedAt is when the script saw the disable; AD's whenChanged is the last change to the object, not necessarily the disable time.

Phase 2

Build the Offboarding Workflow in n8n

This is the workflow that does the actual work. Five nodes, each one closing a gap that manual offboarding leaves open.

Graph permissions for this workflow

Grant the app registration these application permissions (with admin consent): User.RevokeSessions.All (revoke sessions), User.Read.All (check that the disable has synced), GroupMember.ReadWrite.All (list and remove group memberships), and MailboxSettings.ReadWrite (auto-reply and inbox rule). The mailbox calls only work if the user has a licensed Exchange Online mailbox.

Node 1: Revoke Entra ID Sign-In Sessions

This is the step that most manual offboarding processes skip entirely, and it is the single most important one in this workflow.

StepAction
1Set up OAuth2 (client credentials) for Microsoft Graph with the permissions listed above
2Confirm the disable has reached Entra ID: an HTTP Request node with GET https://graph.microsoft.com/v1.0/users/{{ $json.samAccountName }}@iamlab.onmicrosoft.com?$select=accountEnabled, then an IF node. If accountEnabled is still true, go to a Wait node (60 seconds) and loop back. The delta sync from the script usually lands within a couple of minutes
3Once accountEnabled is false, add an HTTP Request node (or the Microsoft Entra ID node if your n8n instance has it). Method: POST
4URL: https://graph.microsoft.com/v1.0/users/{{ $json.samAccountName }}@iamlab.onmicrosoft.com/revokeSignInSessions
Why this comes first

Revoking sign-in sessions invalidates the user's refresh tokens and Entra browser session cookies (Microsoft notes this can take a few minutes). Apps that go back to Entra ID must sign the user in again, and that fails once the disabled state has synced from AD. Until the next Entra Connect sync, the cloud account is still enabled, which is why the script triggers a delta sync and this node waits for accountEnabled to be false before it revokes. Access tokens already issued can stay valid until they expire, and apps with their own sessions, such as AWS IAM Identity Center, need their own step (below).

Node 2: Remove Group Memberships

Synced groups (created in AD and synced by Entra Connect, like SG-Cloud-Admins from Post 2) were already handled by the trigger script, because AD is their source of authority and Graph cannot change them. This node handles cloud-only groups.

StepAction
1Add an HTTP Request node to list groups: GET /users/{id}/memberOf/microsoft.graph.group?$select=id,displayName,onPremisesSyncEnabled,groupTypes,mailEnabled (the plain /memberOf also returns directory roles and administrative units)
2Add a Filter node that keeps cloud-only groups: onPremisesSyncEnabled not true, not dynamic (groupTypes without DynamicMembership) and not mail-enabled (those are managed in Exchange)
3Add a Split Out node, then an HTTP Request node inside the loop: DELETE /groups/{groupId}/members/{userId}/$ref
4Add a Set node that combines adGroupsRemoved from the webhook with the cloud groups removed here into removedGroups for the audit log
The part that closes the AWS gap

Because AWS IAM Identity Center is SCIM-provisioned from these same groups (Post 3), removing the membership takes the user out of provisioning scope, and on the next provisioning cycle (typically 20–40 minutes, or straight away with Provision on demand) Entra ID deprovisions them in AWS. Groups synced from AD must be changed in AD; the removal reaches Entra ID on the next Entra Connect sync, which the script has already triggered. There is no separate "remove from AWS" group change to forget, which is exactly why federated group-based provisioning is worth setting up correctly the first time.

Close the AWS Session Gap

Deprovisioning blocks new AWS sign-ins, but sessions AWS has already issued carry on. AWS IAM Identity Center ends existing application sessions within about 30 minutes; console and CLI role sessions run until the permission set's session duration expires. AWS offers ending active sessions as a console action, so make it a step in the manager or IAM-team notification:

StepAction
1In the IAM Identity Center console, open Users, choose the user and open the Active sessions tab
2Select the sessions, choose End sessions and type confirm
3Keep permission-set session durations short (for example 1 hour, under Permission sets → Edit), because ending the portal session does not end IAM role sessions already started in the console or CLI

Node 3: Redirect the Mailbox

Rather than reaching for Exchange Online PowerShell remoting inside n8n, this uses two Graph API calls that are more reliable from a webhook-driven workflow: an auto-reply and a forwarding rule.

StepAction
1Add an HTTP Request node: PATCH /users/{id}/mailboxSettings to set automaticRepliesSetting to enabled, with a message pointing senders to the manager
2Add a second HTTP Request node: POST /users/{id}/mailFolders('inbox')/messageRules creating a rule that forwards all mail to the manager's address, where your policy allows it (forwarding a leaver's mail can raise privacy and HR-policy questions, so check first)
Forwarding rule request body
{ "displayName": "Offboarding forward", "sequence": 1, "conditions": {}, "actions": { "forwardTo": [{ "emailAddress": { "address": "{{ $json.managerEmail }}" } }], "stopProcessingRules": false } }

Node 4: Notify the Manager

StepAction
1Add an Email Send or Microsoft Teams node
2To: {{ $json.managerEmail }}
3Message: {{ $json.displayName }}'s access is being revoked. Entra ID sessions revoked, {{ $json.removedGroups.length }} group memberships removed (AWS access is removed on the next provisioning cycle), mailbox auto-reply is on.
4Send a second message to the IAM team with a link to the user in IAM Identity Center, so someone ends the user's active AWS sessions (above)

Node 5: Audit Log

StepAction
1Add a Google Sheets node pointing at the same IAM Audit Log sheet from Post 4
2Map: Timestamp = {{ $now }}, Action = USER_OFFBOARDED, User = {{ $json.displayName }}, Groups Removed = {{ $json.removedGroups.join(", ") }}, Status = COMPLETED
What you just built

A complete offboarding automation: AD disable detected → AD group memberships removed and a delta sync triggered → Entra ID sessions revoked once the disable has synced → cloud-only groups removed (AWS deprovisioned via SCIM on the next provisioning cycle) → mailbox redirected → manager and IAM team notified → audit entry written. The exact audit evidence that "prove access was revoked within 24 hours" requires — generated automatically, every time.

Phase 3

Test End-to-End

Use the same test user from Post 4 — Alex Morgan — to run the full cycle.

StepAction
1Activate the "IAM - Leaver Offboarding" workflow in n8n
2Start Monitor-DisabledUsers.ps1 on DC01
3Disable the test user via PowerShell:
Disable the test user to trigger the workflow
Disable-ADAccount -Identity "amorgan"
StepAction
4Verify: after the delta sync, the user shows as disabled in Entra ID, and the Entra ID audit logs show the user's sign-in sessions being revoked
5Verify: after the next provisioning cycle (or straight away with Provision on demand in the AWS app's Provisioning page), AWS IAM Identity Center shows the user removed or disabled, depending on your provisioning settings — confirming the SCIM cascade fired
6Verify: in IAM Identity Center, end the user's active sessions and check the Active sessions tab shows none
7Verify: an email to Alex Morgan's address gets an auto-reply and, if you enabled forwarding, arrives in the manager's inbox
8Verify: the manager and the IAM team received their notifications
9Verify: the audit log has a new USER_OFFBOARDED row with the removed groups listed

That is a closed loop. One account disabled. Five automated actions, across Entra ID and AWS. Nothing left half-finished for someone to find in next quarter's access review.

Phase 4

Add an AI Offboarding Summary

Post 4 used an AI node to make a provisioning decision. Here, use one to generate something more useful for offboarding: a plain-English access summary, written for whoever has to prove this was handled correctly — your manager, an auditor, or future-you six months from now.

StepAction
1Add an OpenAI or Anthropic node after the group-removal step
2Pass in the user's title, department, and the list of removed groups
3Use this prompt:
AI Prompt for Offboarding Summary
You are an IAM compliance assistant writing an offboarding summary for an audit record. User: {{ $json.displayName }} Title: {{ $json.title }} Department: {{ $json.department }} Groups removed: {{ $json.removedGroups.join(", ") }} Write a two-sentence plain-English summary of what access this person had and confirm it was revoked. Flag anything that looks like unusually broad access for their title (for example, admin groups on a non-admin role).

Append the AI's output as a column in the audit log row. Now every offboarding event carries a human-readable summary and a flag for anything that looks wrong — access that should have been caught at a Mover event but never was, and is only visible now that the person is leaving.

Why this matters for your career

Most IAM automation portfolios stop at onboarding, because onboarding is the half that gets demanded. An offboarding workflow that revokes Entra ID sessions, deprovisions AWS through SCIM, closes the AWS session gap, and produces audit-ready evidence is the half that actually prevents breaches — and it is the half most environments, including real enterprise ones, still do by hand or incompletely. Showing this finished is what tells a hiring manager you understand where IAM programs actually fail.

What to Build Next

  • Mover workflow — detect department changes in AD and reconcile group membership against the new role, removing what no longer applies instead of only adding what's new
  • Privileged Identity Management — now that standing access is cleaned up on exit, add just-in-time elevation so it never accumulates as standing access in the first place
  • Access reviews — schedule a recurring Entra ID Governance review against the AWS app from Post 3, using the SCIM group as the review's source of truth
  • Risk-based Conditional Access — feed Identity Protection's risky sign-in signal into this same n8n instance for an automated response, not just a disable after the fact
